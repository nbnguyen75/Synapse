# Synapse Web — Rules for AI Coding Agents

These rules apply to any AI agent (Claude Code, opencode, etc.) working in this
repo. Read PRODUCT.md, ARCHITECTURE.md, and TECH_STACK.md first — this file is
the enforceable checklist.

## Hard Constraints

- **File naming:** kebab-case for all files under `src/`.
- **Scope:** rules in this file apply to `src/` only.
- **Never break existing logic, layout, or structure** of current source files
  when refactoring or extending them.
- **If a rule here conflicts with an existing pattern in the codebase, ask the
  user before proceeding** — do not silently pick one side.
- Never hand-edit `src/paraglide/**` — it's generated by the Paraglide
  compiler (`bun run generate-translation`, also runs on `postinstall`).
- Never add business logic to `src/components/ui/**` (shadcn primitives stay pure).

## The 5 Golden Rules (General)

1. **Single Responsibility** — one reason to change per file/function/component.
2. **Write for humans** — descriptive names over clever/short ones; no hidden
   side effects or global-state surprises.
3. **Low coupling, high cohesion** — related code stays together; unrelated
   modules stay isolated.
4. **Separate business logic from UI** — no calculation/validation/network
   logic mixed into render/layout code.
5. **Rule of Three** — don't build abstractions "just in case." Write concrete
   code first; extract a shared utility only on the 3rd duplication.

## The 5 Golden Rules (Frontend-Specific)

1. **Smart vs Dumb components** — UI components handle layout/styling only.
   Move fetching, computation, and state orchestration into hooks, utils, or
   stores.
2. **Colocate** — CSS, tests, sub-components, and types live next to the
   component that uses them, inside the same feature folder.
3. **Composition over config props** — avoid "swiss-army knife" components
   with many boolean flags; use `children` / compound components instead.
4. **Push state down** — keep state as local as possible; don't lift state
   higher than necessary.
5. **Pure, predictable rendering** — no side effects (API calls, localStorage
   writes) during render.

## When to Split a Component — Concrete Triggers

| Smell                                     | Threshold                                                        | Fix                                                                      |
| ----------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Prop explosion                            | 8+ props, several boolean flags                                  | Split into compound components (`<Card.Header>`, etc.)                   |
| Nested ternary pyramid in JSX             | 2+ nested ternaries controlling render branches                  | Extract early returns / a `<DataBoundary>`-style state-handler component |
| Inline `.map()` with local state/handlers | Any inline handler inside `.map()`                               | Extract to a dedicated `<ListItem />` component                          |
| `useEffect` tower                         | 3+ unrelated `useEffect` blocks in one component                 | Extract each into its own custom hook (`useProfileData()`, etc.)         |
| Prop drilling                             | Prop passed through 2+ intermediate components that don't use it | Use Context/store, or pass the child via composition                     |

## Structural Rules

- **Routes are thin.** `routes/**` files only: define the route, call
  `beforeLoad` guards, render one component from `features/`. No JSX bodies,
  no business logic, no direct API calls in route files.
- **Feature-first placement.** New code starts inside the relevant
  `features/<name>/{api,components,hooks,store,types,utils}/` folder. Do not
  create it in `components/common/` or `hooks/` preemptively — promote it there
  only when a third feature needs it (Rule of Three).
- **Always use `@/` path aliases** — never write `../../../../` relative import chains.
- **Auth guard pattern:** auth state in `features/auth/store/useAuthStore.ts`;
  route protection via `beforeLoad` in `routes/_authenticated.tsx`, redirecting
  to `/login` with a `redirect` search param.
- **API calls go through the Kong gateway base URL** — never hardcode a direct
  service URL (Auth/Notes/AI) in client code.

## Cleanup Rule

- Deleting a feature = delete `src/features/<name>/` + its route file(s) in
  `routes/` + its i18n keys. Leave nothing orphaned.

## Before Writing Code, an Agent Should

1. Check which existing feature folder the change belongs to (or whether it's
   genuinely new).
2. Check `TECH_STACK.md` before reaching for a new library — most needs
   (forms, dates, charts, motion, icons, markdown, streaming AI text) are
   already covered by an installed dependency.
3. Run `bun --bun check` mentally against the golden rules above before
   considering a change "done" (this is what lint-staged/husky will enforce
   on commit anyway).

## No Magic Numbers or Strings

Any literal number or string with implicit meaning (status codes, timeouts,
breakpoints, role names, magic thresholds, repeated string keys, etc.) must be
extracted into a named constant or enum — no inline literals whose meaning
requires guessing from context. This extends the existing "Write for Humans"
golden rule into an enforced check: a reviewer (human or agent) should be able
to name what a value means without searching for where it's used.

Examples:

```ts
// ❌ Bad
if (res.status === 404) { ... }
setTimeout(fn, 3000)

// ✅ Good
import { StatusCodes } from 'http-status-codes'
const RETRY_DELAY_MS = 3000

if (res.status === StatusCodes.NOT_FOUND) { ... }
setTimeout(fn, RETRY_DELAY_MS)
```

## React Compiler Lint Rules — Known Failure Patterns

These are enforced by the `@eslint-react` ruleset (via oxlint) and will fail
`bun run check`/`lint`. Do not generate code that triggers them.

### 1. Never create components during render (`@eslint-react/static-components`)

Resolving a component reference (e.g. picking an icon component from a map/lookup
function) inside the render body and then using it as JSX creates a **new**
component identity every render, resetting any internal state it holds.

```tsx
// ❌ Bad — Icon is a new component reference every render
function ExperienceCard({ exp }) {
  const Icon = resolveLucideIcon(exp.icon);
  return <span>{Icon ? <Icon className="w-4 h-4" /> : null}</span>;
}

// ✅ Good — resolve to a component reference, but do it as a stable value,
// not by wrapping/creating a component inline. If resolution itself is cheap
// and pure (a lookup, not a factory), memoize it so identity is stable:
function ExperienceCard({ exp }) {
  const Icon = useMemo(() => resolveLucideIcon(exp.icon), [exp.icon]);
  return <span>{Icon ? <Icon className="w-4 h-4" /> : null}</span>;
}
```

Rule of thumb: if a function returns "a component to render," never call that
function fresh on every render and hand its result straight to JSX without
memoizing it — either hoist the resolution to module scope (if it doesn't
depend on props), or wrap it in `useMemo` keyed on the actual dependency.

### 2. Never call `setState` synchronously inside a plain `useEffect` body (`@eslint-react/set-state-in-effect`)

The lint rule tracks **when** `setState` runs, not how it's spelled. Wrapping
the call in a local function does **not** fix it if that function is still
invoked synchronously within the effect body — same tick, same problem.

```tsx
// ❌ Bad — direct synchronous call
useEffect(() => {
  if (defaultExpandedId && expandedId === null) {
    setExpandedId(defaultExpandedId);
  }
}, [defaultExpandedId]);

// ❌ Still bad — wrapping in a local function changes nothing;
// sync() is still called synchronously in the same effect execution
useEffect(() => {
  function sync() {
    if (defaultExpandedId && expandedId === null) {
      setExpandedId(defaultExpandedId);
    }
  }
  sync();
}, [defaultExpandedId]);
```

**If the effect's only job is syncing a prop/parent state into local state**,
that's a sign you don't need an effect at all — derive the value during render,
or seed it once via the state initializer:

```tsx
// ✅ Best — derive it, no state or effect needed
const activeExpandedId = expandedId ?? defaultExpandedId;

// ✅ Or, if it must be mutable local state, seed it at init time
const [expandedId, setExpandedId] = useState(defaultExpandedId);
```

**A local function is only a valid fix when it's a callback for something
genuinely async** — an event listener, a subscription, a timeout, a promise
`.then()` — because then `setState` fires in a later tick, outside the
effect's own synchronous execution:

```tsx
// ✅ Good — local function as an async callback, genuinely deferred
useEffect(() => {
  function handleChange(value) {
    setExpandedId(value); // fires later, when the event happens
  }
  externalStore.subscribe(handleChange);
  return () => externalStore.unsubscribe(handleChange);
}, []);
```

### Checklist before writing a `useEffect`

- [ ] Is this reacting to React's own state (props/state)? → don't use an effect;
      derive the value in render, or seed it via the state initializer.
- [ ] Is this syncing with a truly external system (DOM API, subscription,
      timer, browser API)? → effect is appropriate.
- [ ] If I wrapped the `setState` call in a local function, is that function
      called **synchronously in the effect body** (still wrong) or **only from
      an async callback** (fine)?
- [ ] Am I about to hand a freshly-computed value to JSX as if it were a
      component? → memoize or hoist it first, don't inline-create (see rule 1).

## i18n Rules

- All user-facing strings go through Paraglide: `import { m } from '@/paraglide/messages'`,
  then `m.some_key()`. No hardcoded UI strings, no `useTranslation()` hook.
- Key naming: `[feature]_[component]_[element]` (e.g. `notes_editor_save_button`).
- Add new keys to **both** `messages/en.json` and `messages/vi.json` in the
  same change — never add a key to only one language file.
- When deleting a feature, delete its `[feature]_*` keys from both message files too.
- **Never call a Paraglide message function dynamically via a stored key**
  (e.g. `m[dynamicKey]()`, or a `labelKey` field on a config object that gets
  invoked later as `m[item.labelKey]()`). Paraglide's compiler relies on
  static, literal call sites (`m.some_key()`) to extract and tree-shake
  messages — a dynamic/indirect call breaks that analysis and can silently
  produce missing translations or dead-code-elimination bugs.

  Instead, resolve the mapping through an explicit `switch`/lookup **function**
  that calls each message function literally, the same pattern used for
  `getTranslatedAuthErrorMessage` (auth error codes → messages):

```ts
// ❌ Bad — dynamic key, m[...] is not a static call site
export const SORT_OPTIONS = [
  { labelKey: 'notes_page_sort_updated' as const, value: 'updatedAt_desc' },
  {
    labelKey: 'notes_page_sort_created_new' as const,
    value: 'createdAt_desc',
  },
  // ...
] as const;

// usage: m[option.labelKey]()  ← breaks static extraction

// ✅ Good — config stays data-only (no message calls in it)...
export const SORT_OPTIONS = [
  { key: 'updated', value: 'updatedAt_desc' },
  { key: 'createdNew', value: 'createdAt_desc' },
  { key: 'createdOld', value: 'createdAt_asc' },
  { key: 'titleAz', value: 'title_asc' },
  { key: 'titleZa', value: 'title_desc' },
  { key: 'readLong', value: 'readTime_desc' },
  { key: 'readShort', value: 'readTime_asc' },
] as const;

// ...and a dedicated getter does the literal, static lookup
export function getSortOptionLabel(key: (typeof SORT_OPTIONS)[number]['key']) {
  switch (key) {
    case 'updated':
      return m.notes_page_sort_updated();
    case 'createdNew':
      return m.notes_page_sort_created_new();
    case 'createdOld':
      return m.notes_page_sort_created_old();
    case 'titleAz':
      return m.notes_page_sort_title_az();
    case 'titleZa':
      return m.notes_page_sort_title_za();
    case 'readLong':
      return m.notes_page_sort_read_long();
    case 'readShort':
      return m.notes_page_sort_read_short();
  }
}
```

This mirrors `getTranslatedAuthErrorMessage`'s `switch (code) { case '...': return m.xxx(); }`
shape — every branch is a literal `m.xxx()` call the Paraglide compiler can see.
